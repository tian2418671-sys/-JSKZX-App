## 〇、数据模型实证（v4.1 写全，消除歧义）

### 0.0 memory_items 表结构（现状 = 已核实）

```sql
CREATE TABLE memory_items (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  type TEXT NOT NULL,          -- fact | summary | message
  content TEXT NOT NULL,
  key TEXT,                    -- ✅ v2 已存在：记忆表格键（名字/喜欢/位置…）——D4 依赖它，无需新增
  card_name TEXT,              -- 现状存显示名 → v4.1 降级为纯展示
  created_at INTEGER NOT NULL
);
```

**关键结论**：`key` 列**已存在**（v1→v2 迁移加入），JS 链路 `recordFact(f.key,…)` → `recordMemory('fact', v, key, cardName)` → `api.memoryAdd({type, content, key, cardName})` **全程有 key 传递**。D4 同 key 覆盖可直接基于 `key + card_path` 实现，无需改 JS 传参。

### 0.1 schema v3（本次迁移目标）

```sql
ALTER TABLE memory_items ADD COLUMN card_path TEXT;     -- 卡唯一标识（库内相对路径），记录/注入/查看按它
ALTER TABLE memory_items ADD COLUMN updated_at INTEGER; -- D4 覆盖时刷新；降级排序按它
ALTER TABLE memory_items ADD COLUMN confirmed INTEGER DEFAULT 1; -- P0=1 照常注入；P1 改为新 fact=0 待确认
CREATE INDEX IF NOT EXISTS idx_mem_card_path ON memory_items(card_path, type);
CREATE INDEX IF NOT EXISTS idx_mem_card_upd ON memory_items(card_path, updated_at);
```

**列语义**：
- `card_path` = 卡唯一标识（`card.value.path`），所有读写按它
- `card_name` = 纯展示（迁移时填显示名；新写入填 `card.value.name`）
- `confirmed` = P0 阶段恒为 1（注入照常）；**P1 上线确认 UI 后才改为新 fact 写 0**

### 0.2 记忆链路全景（v4.1 修订点标注）

```
写入流  CardDetailView.sendChat（CardDetailView.vue:2376-2380）
```

## 二、分阶段方案

### P0 · 数据治理（最小因果链）

#### D1 卡级隔离（card_path 分桶）

1. **schema v3 迁移**（0.1）：新增 `card_path` / `updated_at` / `confirmed` 三列 + 两索引；`DB_VERSION` 2 → 3；`onUpgrade` 增量执行（对齐 `SqliteMetaPlugin` user_version 模式）。
2. **原生 `MemoryPlugin`**：
   - `add`：读 `cardPath` 参数写入 `card_path`；`card_name` 单独入展示列；`updated_at = created_at`。
   - `search`：新增 `cardName` 参数；**非空时强制 `AND card_path = ?`**；空 query 分支**必须 cardName 非空**才走"最近 N 条"（否则 reject）。
   - `list`：新增 `cardName` 参数，同款过滤。
   - `update`：刷新 `updated_at`。
3. **JS 层**：`searchMemory(query, limit, cardPath)`、`listMemory(type, limit, cardPath)`、`buildMemoryContext(query, cardPath)` 透传；`normalizeMemoryItem` 增加 `cardPath` 字段映射。
4. **`CardDetailView.vue` 注入调用**（2256/2303 两处）：`buildMemoryContext(lastUserText, card.value.path)`；记录调用（2377-2380）传 `{ path: card.value.path, name: card.value.name }`。
5. **查看器按卡过滤**：`TestSidebar` 新增 prop `currentCardPath`（CardDetailView 所有打开侧边栏的入口都传）；`refreshMemoryList` 透传；顶部显示当前卡 chip + "只看本卡/全部" 切换，**默认只看本卡**。

#### D1a 路径变更钩子

- `renameCardTo` / `moveCardToGroup` / `removeCard`（`useMobileLibrary.js:1129/1157/1174`）挂接：
  - rename/move → `UPDATE memory_items SET card_path = 新path WHERE card_path = 旧path`（事务 + 幂等；from 不存在则跳过；to 已存在则合并去重）
  - remove → `DELETE WHERE card_path = ?`
- 新增桥接 `memoryMigrateCard({ from, to })` + `memoryClearByCard({ cardPath })`。

#### D2 检索治理

1. **停用词表**（JS `useChatMemory.js`）："我/你/的/了/是/在/吗/呢/继续/好/嗯…"，集中常量可配置。
2. **有效词 <2 降级**：`searchMemory(query='', cardPath, limit)` → 本卡最近 N 条，**排序 `updated_at DESC`**（不是 created_at，避免 D4 覆盖后旧序）；N = I2 条数。
3. **空 query 防护**：原生 search 空 query 且无 cardName → reject（绝不返回全库）。

#### D3 事实规则收紧

- 融合 `useChatFactExtractor.js` 规则面（7 领域：identity/preference/relation/location/goal/memo/health），**先修剪重复规则**（"记住|记下|记一下|记一下"重复、`[:：]\s*(.+)` 过宽兜底）。
- 值上限：普通 30 字；显式指示词（记住/我叫/我今年）80 字；**统一截断先于转义**。
- 排除：疑问句、否定假设（如果/要是/假如）、引用（他说…）。
- key 枚举提为单一常量源 `FACT_KEYS`（D3 提取与 I4 分类共用）。
- 单测：`test/` 新增"我在思考…"返回空、"我的想法是…"返回空。

#### D4 同 key 覆盖更新

- `MemoryPlugin.add`：type=fact 且 key 非空时，查 `key + card_path` 冲突：
  - 冲突 → `UPDATE content=新值, updated_at=now`（**保留首次 created_at**）
  - 无冲突 → 插入
- confirmed 语义：**P0 阶段新 fact 写入 `confirmed=1`（照常注入）**；P1 收紧为 0。
- 兜底：单卡 fact 上限 50 条（防极端膨胀，超出删最旧）；message 维持每卡 40 条修剪。

#### I2 注入上限

- `jsmobile-memory-limit` 默认 **20 → 8**（钳 1-200）；新增 `jsmobile-memory-inject-tokens` 默认 200，**硬上限 400**（防中文 token 估算误差）。
- `buildMemoryContext` 按"条数 + 估算 token"双约束截断（复用 tokenEstimate）。

#### I4 注入格式 C

```xml
<memory>
<user_profile>
  名字：星野
  喜好：红色的花
</user_profile>
<recent_events>
- 星野在图书馆遇到主角
</recent_events>
</memory>
```

- 空记忆整体跳过；截断先于转义；`jsmobile-memory-format`（C/markdown）默认 C，P1 设置页下拉。

#### I5 注入 debug

- `buildMemoryContext` 返回 `{ text, meta }`；meta = { 注入条数, 来源卡 path, 降级与否, 估算 token }。
- **调用点仅 2 处**（`CardDetailView.vue:2256/2303`），同步适配 `memCtx.text` / `memCtx.meta`。
- TestSidebar 记忆区展示 meta。

#### B1 批量测卡抑制

- 入口：`CardLibraryView.vue` 批量模式（batchMode）**进入时记住原记忆状态并临时关闭，退出时恢复**（不简单 set false）。
- 兜底：批量写入路径被误调时先查批量状态再写。

#### 迁移 + 灰度

- **7.1 显示名 → card_path 迁移**（一次性，事务 + 幂等 + 可重跑）：
  - 显示名唯一匹配某卡 → `card_path = 该卡 path`，`card_name = 显示名`（展示保留）
  - 多卡同名 → `card_path = NULL`（**遗留桶**），`card_name = 显示名` 保留；查看器顶部提示"N 条未归属当前卡"
  - 无匹配（卡已删）→ `card_path = NULL` 同进遗留桶（不丢数据）
- **7.2 schema 版本化**：`DB_VERSION` 2 → 3，`onUpgrade` 增量；迁移脚本幂等（`ALTER TABLE ... ADD COLUMN` 前查列存在）。
- **7.3 灰度 flag**：`jsmobile-memory-v2`；关闭走旧路径（旧分桶/旧格式/旧条数）。**注意**：灰度关闭时新旧数据分桶不同（path vs NULL），注入走旧路径（card_name 过滤）不受影响；开启后按 card_path。
- **双写过渡**：P0 上线后新写入用 card_path；旧数据一次性迁移；不长期双写。

## 七、第二轮评审细节定案（v4.1 补充）

### 7.1 D4 单卡 fact 上限删除策略

**问题**：50 条上限超出时"删最旧"，但 D4 覆盖时保留首次 created_at 并刷新 updated_at，按 created_at 删除会误删刚更新的 fact。

**定案**：**按 `updated_at ASC` 删除最旧**。理由：
- 被频繁覆盖的 fact 说明用户反复修改/强调，updated_at 最新，不应被删
- 很久未被覆盖的 fact（updated_at 很旧）更可能已过时或无用，应优先淘汰
- 不影响 `created_at` 的"首次创建时间"语义

**实现**：`MemoryPlugin.add` 写入后执行检查：
```java
// D4 兜底：单卡 fact 上限 50 条，超出按 updated_at ASC 删最旧
int count = db.rawQuery("SELECT COUNT(*) FROM memory_items WHERE type='fact' AND card_path=?", new String[]{cardPath}).getCount(0);
if (count > 50) {
    db.execSQL("DELETE FROM memory_items WHERE type='fact' AND card_path=? AND id NOT IN (SELECT id FROM memory_items WHERE type='fact' AND card_path=? ORDER BY updated_at DESC LIMIT 50)", new String[]{cardPath, cardPath});
}
```

### 7.2 D1a 合并去重冲突规则

**问题**：`renameCardTo` / `moveCardToGroup` 时，若目标 path 已存在同 `key + type` 的记忆，冲突规则未定义。

**定案**：**目标优先，删除源**。理由：
- 用户主动 rename/move 意味着卡的归属意图变更，目标路径的数据应被视为最新状态
- 实现简单，事务内先写目标再删源，失败可回滚
- 不同 key 不冲突，仅同 key+type 冲突时触发

**实现**（事务内）：
1. 查询源路径所有记忆
2. 对每条记忆，查目标路径是否有同 key+type：
   - 有 → 跳过（目标优先），或可选择"更新目标的 content 为源的值"（保留源的数据为最新）
   - 无 → 直接 INSERT 到目标
3. 全部写入后 DELETE 源路径全部记忆
4. 任意步骤失败 → 事务回滚

**写入单测**：`test/memoryMigrate.test.mjs`，覆盖"源有/目标有/两边都有/两边都空"四种情况。

### 7.3 I5 灰度关闭时 meta 兼容

**问题**：`jsmobile-memory-v2` 关闭时走旧路径，`buildMemoryContext` 返回 `{text, meta}` 结构，调用点需兼容。

**定案**：**统一返回 `{text, meta}` 结构**，无论灰度开关状态：
- 开启（新路径）：`{ text: '...', meta: { injectedCount, cardPath, isDegraded, estimatedTokens } }`
- 关闭（旧路径）：`{ text: '...', meta: null }`
- 调用点判断：`const memCtx = await buildMemoryContext(...)`；注入用 `memCtx.text`（旧版为 string 直接使用，需统一）；debug 展示用 `if (memCtx.meta) { ... }`（meta 为 null 则不展示 debug）。

**调用点改造**（仅 2 处）：`CardDetailView.vue:2256/2303`，`memCtx = ...` 改为 `const memCtx = await buildMemoryContext(...)`，`if (memCtx) sysParts.push(memCtx)` → `if (memCtx.text) sysParts.push(memCtx.text)`。

### 7.4 recordMessage 签名扩展

**问题**：R1 要求传 `{ path, name }` 对象，现有签名是 `recordMessage(role, content, cardName)`，第三参是字符串。

**定案**：**第三参支持 string 或 object**，函数内部自动处理，保持向后兼容。

**新签名**：
```javascript
export function recordMessage(role, content, card) {
    // card: string（旧调用，兼容）或 object { path, name }（新调用）
    const cardPath = typeof card === 'object' ? (card.path || '') : (card || '');
    const cardName = typeof card === 'object' ? (card.name || '') : (card || '');
    // ... 调用 recordMemory 时传 cardPath 为主键，cardName 为展示
}
```

**调用点改造**（全仓仅 2 处，`CardDetailView.vue:2377-2378`）：
- 旧：`recordMessage('user', processedText, card.value.name)`
- 新：`recordMessage('user', processedText, { path: card.value.path, name: card.value.name })`

旧调用（传字符串）在新签名下自动走 `cardPath = 旧字符串`，不过不会出现在本项目中，向后兼容仅作保险。

### 7.5 迁移脚本边界用例

**问题**："显示名唯一匹配某卡"的定义需明确，补充边界用例。

**定案**：
- **唯一匹配**：遍历当前卡库（`mobileLibrary.library`），按 `card.name` 分组计数；仅当某显示名只对应一个 `card.path` 时，将该显示名的记忆 `card_path` 更新为该 path。
- **边界处理**：
  - 卡已删除（显示名在库中无匹配）→ `card_path = NULL`（遗留桶），不丢数据
  - 显示名为空（`card_name IS NULL` 或空字符串）→ `card_path = NULL`（遗留桶）
  - `card.path` 为空（理论上不存在，但防御性处理）→ 跳过该卡，不参与迁移匹配
  - 同名卡（多个卡共享一个显示名）→ `card_path = NULL`（遗留桶），不强制拆散

- **迁移脚本位置**：`MemoryPlugin.java` 的 `DB_VERSION` 2→3 `onUpgrade` 内，从 `memory_items` 读取所有 distinct `card_name`，从 `LibraryFsPlugin` 获取卡库列表（需要跨 plugin 通信，或由 JS 层传入卡列表）。

**跨 plugin 通信决策**：迁移在 `MemoryPlugin.onUpgrade` 时无法访问卡库数据。**改由 JS 层执行迁移**：在 `useChatMemory.js` 增加 `migrateMemoryToV2(cardList)` 函数，`cardList` 由 CardDetailView 或 CardLibraryView 初始化时传入（`mobileLibrary.library`）。Java 层只负责 schema 升级，JS 层负责数据迁移。

### 7.6 查看器"全部"视角范围

**问题**："全部"应包含哪些记忆？

**定案**：**"全部" = 当前卡 + 遗留桶**（不含其他卡的记忆）。理由：
- 测卡场景中用户关注的是当前卡和未归属的遗留数据，其他卡的记忆不应混入当前上下文
- 实现简单：`WHERE card_path = 当前卡path OR card_path IS NULL`
- 顶部 chip 显示"本卡 X 条 + 遗留桶 Y 条"，清晰明了
- 若用户需要查看特定其他卡的记忆，通过切换卡片进入该卡的"本卡"视角

### 7.7 性能压测数据集构造

**问题**："两万卡下 search P95 < 50ms"需要明确测试环境和数据构造方法。

**定案**：
- **数据集构造**：`scripts/` 下新增 `gen-memory-bench.mjs` 脚本：
  - 生成 N 张卡（参数化，默认 20000），每卡 path = `test/card_{i}.json`
  - 每卡 50 条 fact + 40 条 message = 90 条
  - 总计 20000 × 90 = **180 万行**
  - fact 内容随机填充（停用词 20% + 有效词 80%，模拟真实分布）
  - 通过 `MemoryPlugin.add` 批量写入（事务批量插入加速）
- **测试环境**：中端 Android 设备（骁龙 7 系 / 6GB RAM）
- **测试用例**：
  - 热查询：连续 100 次 search，每条 query 包含 3-5 个有效词，统计 P50/P95/P99
  - 冷查询：首次查询（无缓存），统计耗时
  - 降级查询：空 query + 卡过滤（最近 N 条）
  - 注入构建：`buildMemoryContext` 端到端耗时
- **验收基准**：
  - 热查询 search P95 < 50ms
  - 降级查询 P95 < 20ms
  - 注入构建端到端 P95 < 20ms
  - 内存占用增长 < 50MB（对比无记忆状态）
