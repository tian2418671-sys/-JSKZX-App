## 一、Bug 复盘

### 🔴 教训 1：详情页打开「加载半天」——watch 监听引用型数据在渐进式推送下触发风暴

**用户反馈**：点开卡片详情页面要加载半天。

**根因**（`js/mobile/views/CardDetailView.vue`）：

库加载是**渐进式分批 push**（千卡库 ~80 批）。原兜底 watch 监听 `mobileLibrary.library`
这个数组引用，**每批 push 都会触发一次 watch**；水合（`hydrateCardForEdit`）未完成期间
`card` 为空，于是每批触发一次 `hydrateCardForEdit`——**同卡并发整卡读取 N 次**（每次都是一次
桥接 IPC + 全量解析），互相抢桥线程，越堆越慢，表现为「加载半天」。

**修复**：

1. watch 内加 `!mobileLibrary.ready` 守卫——库正在分批加载时不触发，只在库完整就绪后兜底；
2. 加 `hydrating` 布尔锁——水合进行中去重，同卡只读一次；
3. `loadCardFullData` 加**并发去重缓存**（path → in-flight Promise，完成后立即失效）。

**教训检查清单**：

- [ ] watch 监听的如果是会被**高频增量修改**的数组/对象（push/splice），必须想清楚触发次数；
- [ ] 「兜底重试型 watch」必须自带**去重锁**（进行中标记），否则并发执行 N 份完全相同的工作；
- [ ] 渐进式 UI（分批加载）与「等待数据到达」类逻辑天生冲突，优先等 `ready` 标志而非监听内容变化。

### 🔴 教训 2：快照删除「永远报非法路径」+ 保存自动备份无视用户开关

**用户反馈**：点开快照删除功能，反而会再多一个快照（多余）。

**根因 A**（`js/bridge/android.js` `deleteCardSnapshot` / `deleteWorldbookSnapshot`）：

安全检查写成 `sRel.includes('/.bak_history/')`（要求**前导斜杠**），而 `toRelativePath`
返回的是 `'.bak_history/xxx'`（**相对路径无前导 /**）。该条件**恒为 false** → 删除必然被
拦截并提示「非法快照路径」。**删除功能从上线起就从未生效过。**

**根因 B**（`CardDetailView.vue` `save()`）：

保存前的自动备份**不读设置页「自动快照」开关**，无论用户是否关闭都会生成备份快照。
用户每次点保存就多一份 `.bak_history` 快照——与他「我只要删除，别给我添东西」的预期冲突，
表现为「点快照操作会多一个快照」。

**修复**：

1. 安全检查改为匹配相对路径前缀（`== '.bak_history'` 或 `startsWith('.bak_history/')`）；
2. 保存自动备份读取 `snapshotConfig.enabled` + `cooldownMs`（短缓存 10s 避免每存必查配置），
   用户关闭自动快照后保存不再产生备份。

**教训检查清单**：

- [ ] **路径前缀/包含校验必须拿真实数据跑一遍**——写 `'/a/b/'` 包含检查时，确认调用方传的
      就是那个形态（本项目相对路径无前导 /，`includes('/dir/')` 永远 false）；
- [ ] 前置校验（return error）是「保住错误」而不是「保住功能」——上线前要测**主路径真的能成功**；
- [ ] 每新增一个自动行为（自动备份/自动打标），先问：用户**有没有开关能关掉它**？开关是否被真正读取？

### 🟡 教训 3：重操作按钮缺少重入锁（上一轮已修，此处存档）

**用户反馈**：刷新按钮、+号按钮反应缓慢。

**根因**：刷新 = 全库重扫（图标按钮与下拉刷新双绑同一逻辑），连点会叠加多次全库重扫；
导入文件选择器可被连点弹出多次；全程序多个「整文件读写」按钮（保存/快照/批量删除等）均无
重入锁，快速连点导致多次整图 base64 过桥排队。

**修复**：1.2s 节流 + 进行中互斥 + 全程序 async 重操作统一加布尔锁（详见 CHANGELOG 1.10.19）。

## 四、BUG-14 · 800 卡秒开后「点详情极慢」——原生桥单线程被 scan 独占（2026-09-14）

**用户反馈**：800 张卡加载速度没问题，但加载完成后点开详情页反应缓慢至极。

**根因**：**Capacitor 把所有 `@PluginMethod` 串行在同一条 "CapacitorPlugins" bridge 线程上**执行。
800 卡的一次 `scan()`（全树 `buildRelIndex` + 8 路 `fillMtimesParallel`）会**独占该线程 5~9 秒**
（实测 scan=7871ms；并发 readText 第 2 次≈第 1 次的 2 倍 → 证明串行排队）。列表靠轻量缓存**秒开**
（所以「加载没问题」），但秒开后 `reconcileLibraryInBackground` 立即发起全量 `scan` + 逐批
`readCharaBatch`，全部排在同一桥线程上。这期间用户点开任意卡 → 详情页的
`readCharaBatch`/`readText`/`readThumb` 只能干等（实测排队 **5596ms**，闲时仅 33ms）→ 「极慢」。

**为什么之前没发现**：
- 详情页自身代码链路没问题（小卡稳态点开只要 269ms，水合 45ms，无长任务）；
- 问题只在**「缓存秒开 + 后台 reconcile 扫描」这个并发窗口**里才暴露，单卡、小库、稳态都测不出；
- 「秒开」本身掩盖了后台仍在扫描的事实。

**修复**（`LibraryFsPlugin.java`，沿用项目内 `readThumbBatch` 已用的 `BATCH_ORCH` 异步模式）：
1. **重活离开桥线程**：`scan` → `SCAN_EXEC`（单线程）；`readTextBatch` / 大 `readCharaBatch` /
   `getFileStats` → `BATCH_EXEC`（单线程编排，批内仍开 8 路 worker）。桥线程立即返回。
2. **前台读取快速通道**：单文件 `readText`、`readCharaBatch([≤2 卡])`（详情水合正走这条）→
   `FAST_EXEC`（2 线程），**不排在后台 reconcile 的几十批读之后**。
3. 子线程 `call.resolve()` 安全：`sendResponseMessage → Bridge.eval → 主线程 evaluateJavascript`
   自动切主线程；`relIndex`=ConcurrentHashMap、`scanFilesList`/`relIndexReady`=volatile 保证可见性。

**验证**（CDP 真机，804 卡，扫描进行中连续点开卡片）：

| 场景 | 修复前 | 修复后 |
|------|--------|--------|
| PNG 卡读取排队 | 5596ms | 详情打开 ~230ms |
| 扫描早期点卡 | ~5.6s | 244ms |
| 扫描中期点卡 | ~5.6s | 272ms |
| 扫描后期点卡 | ~5.6s | 239ms |

`npm test` →134/134 pass。

**教训检查清单**：
- [ ] **凡是「重 IO 的 PluginMethod」必须移交专用线程池**——Capacitor 桥线程全局唯一，
      一个 `scan`/批读 就能把**所有**其它插件调用（包括 UI 立即要用的读取）堵死。
- [ ] **前台即时读取要开「快速通道」**，绝不能和后台批处理共用一条串行队列，
      否则用户操作会被自己 App 的后台任务饿死（本 bug 的本质）。
- [ ] 判断桥是否串行：并发发两个相同读调用，**第 2 个耗时≈第 1 个的整数倍**即串行
      （本项目 readText：579 → 1064）。
- [ ] 「加载没问题」≠「系统空闲」——秒开往往意味着后台还有活没跑完；测交互延迟要覆盖
      **刚加载完的并发窗口**，不能只测稳定态。
- [ ] 大文件「整文件过桥」也有隐性成本（HEAVY 卡 readText≈550ms 过桥），但远小于「排队」；
      **先测并发/排队，再测单点性能**，否则南辕北辙。
