## 一、背景：为什么 P1 不能只「加 4 个方法」

执行版 §3.2 只给了 4 个插件方法（权限状态 / 请求授权 / 路径浏览 / 设置库根），但 `buildScanResult()` 仍走
`rootFile()`（SAF）。若只照抄，全盘模式**选完目录就报「尚未选择库目录」**（核验 §C.2-3）。

本批次补齐了「路径后端」真正可用的实现：

| # | 实现 | 位置 |
| --- | --- | --- |
| 1 | **`FileDocumentFile` 适配层**：把 `java.io.File` 包成 `DocumentFile`，使既有 43 处 SAF 调用点零改动复用（`renameTo`/`delete`/`createFile`/`listFiles`/`length`/`lastModified` 全部走 File 语义） | `androidx/documentfile/provider/FileDocumentFile.java`（同包，因 `DocumentFile(parent)` 为包级私有构造器） |
| 2 | `rootFile()` 按后端分派：路径模式返回 `FileDocumentFile(根路径)` | `LibraryFsPlugin.java` |
| 3 | `buildRelIndex()` 增加 `buildRelIndexByPath()`：遍历 File 树产出同构的 `scanFilesList/scanDirsList/docInfoCache/relIndex` | 同上 |
| 4 | 流分派：`openIn/openOut`（DocumentFile）与 `openByUri/openOutByUri`（Uri）按 `file:` / `content:` 分流，覆盖 `readStream/writeStream/writeUriFromStream/decodeThumbBitmap` 及 8 处直接调用 | 同上 |
| 5 | 树操作分支：`doMove()` 路径模式改 `File.renameTo`；`writableDirByRel()` 路径模式直接 `mkdirs` | 同上 |
| 6 | `libraryInfo()` 增加路径后端分支（`backend:"path"` + `persisted:true` + 路径级 `reason`） | 同上 |
| 7 | 4 个插件方法落地（API<30 明确 `supported:false`，不假装可用） | 同上 |
| 8 | Manifest：`xmlns:tools` + `MANAGE_EXTERNAL_STORAGE` + `READ_EXTERNAL_STORAGE(maxSdk=32)`；`WRITE` 保留原有 `maxSdk=28`（不重复声明） | `AndroidManifest.xml` |
| 9 | JS 桥接 4 个方法 + `contract.js` 校验清单登记 | `js/bridge/android.js` / `contract.js` |
| 10 | 设置页「全盘路径模式」入口 + 内置目录浏览器（卷切换 / 面包屑 / 目录列表 / 使用此目录） | `SettingsView.vue` |

## 五、边界与遗留

1. **`Android/data`、`Android/obb` 仍不可读** —— 官方限制（连 `MANAGE_EXTERNAL_STORAGE` 也排除），路径浏览器会提示"目录不可读"。
2. **API < 30 不支持全盘模式**：项目 `minSdk 24` 且无运行时读权限申请流程，`allFilesAccessState.supported=false`；这些设备继续走 SAF。
3. **外部世界书/预设目录** 仍走独立 `treeUri`（SAF），不受主库后端切换影响（终审 §3.3 说明一致）。
4. **`file://` URI 与系统组件**：路径后端下 `openPath`/`openGlobalTrash` 这类交给系统 App 的 Intent 在 API 24+ 会触发 `FileUriExposedException`，需走 `FileProvider`（`file_paths.xml` 已含 `external-path`）。**P1 未改这两处，属已知遗留**，下次迭代补。
5. 真机（OPPO/ColorOS）需复验：权限跳转返回、SD 卡/OTG 卷切换、大目录浏览性能。
