## 一、TL;DR

用户反馈的"记忆对测卡内容全量记录、混乱、干扰上下文"**不是玄学，代码证据确凿**。按严重度排序的根因：

1. **检索不按卡隔离**：`MemoryPlugin.search` 无 `card_name` 条件 → 注入"所有卡最近命中的事实"（跨卡污染，头号根因）
2. **检索词过宽**：整句用户消息 OR-LIKE 模糊匹配，常用字全命中 → 实际注入"全卡池最近 20 条"
3. **事实提取规则误吞整段文本**："我在思考…"/"我的想法是…"记成整段长文 fact 并灌进 system
4. **事实无更新、无限膨胀**：同 key 不同值反复插入；`summary` 是死代码
5. **同名卡串堆**：按显示名分桶，重名卡共享记忆

**v3 路线（对齐 P0 承诺，最小因果链）**：
- **P0 = D1（卡隔离）+ D2 简版（停用词 + 修 AND() + 降级路径）+ D3（规则收紧）+ D4（同 key 覆盖更新）+ I2（注入上限）+ I4 简版（固定格式 C）+ I5（注入 debug 展示）**
- **I1（相关度排序）→ P3**（记忆池收敛前排序是"垃圾放大器"，向量接入后自然消解）
- P0 结束时三大痛点（隔离/误吞/膨胀）的因果链**全部闭合**，与 TL;DR 承诺一致

## 二、记忆功能在测卡场景的定位

### 2.0.1 测卡 vs 长期陪伴：记忆需求的本质差异

| 维度 | 长期陪伴聊天（开源方案主要服务对象） | **测卡场景（本项目）** |
|---|---|---|
| 核心诉求 | 角色"记得"跨会话发生过的事 | 验证人设一致性/文风/边界行为，**需要干净可复现的上下文** |
| 跨会话 fact | 核心价值 | **负资产居多**——用户想干净地测新设定，历史 fact 是污染 |
| 记忆规模 | 无限增长需压缩 | 测完即弃，每卡几十条内 |
| 写入频次 | 长期高频 | 测卡高频；**批量测卡（两万卡）会产生海量垃圾写入** |

### 2.0.2 三条设计红线

1. **记忆默认收敛、可控、可清**：fact 收敛到 key 类别数（D4）；单条可删、一键清空某卡（M1 记忆管理 UI）
2. **批量测卡抑制写入**（红线落地为措施 B1）：批量场景默认关闭记忆写入，或降采样为"仅用户显式指示'记住'的内容"
3. **注入 debug 可见**：测卡用户本就在看完整 prompt——注入的记忆必须能在 debug 面板看到（注入了哪几条、来源卡、相关度、降级与否、总 token）

### 2.0.3 开关粒度设计（纳入 D1）

| 开关层级 | 粒度 | 默认 | 说明 |
|---|---|---|---|
| 全局 | 所有卡记忆开/关 | 开（现状） | 设置页已有 `jsmobile-memory-enabled` |
| 卡级 | 单卡记忆开/关 | 开 | 测卡侧边栏新增；关闭后不写入、不注入该卡记忆 |
| 会话级 | 单会话记忆隔离 | 关 | 默认跨会话共享（by design）；打开后按会话隔离 |
| 批量 | 批量测卡抑制写入 | 开（抑制） | 批量场景默认关写入（B1） |

### 2.0.4 两万卡场景的记忆规模预期

- 现状：无 `card_name` 条件的 LIKE 检索 = **全表扫描**；两万卡时随记忆量线性劣化
- D1 后：`card_name = ?` + `(card_name, type)` 索引命中单卡 ~15 条
- 规模：两万卡 × 每卡 ~15 fact ≈ 30 万行（SQLite 无压力）；L1 message 每卡 40 条 × 两万 = 80 万行（可接受，设置页显示量级 + 一键清空）

## 三、缺陷根因（代码证据）

### 3.1 跨卡检索污染（头号根因）—— P0

- `MemoryPlugin.java:163`：检索 scope 只含 `type IN ('fact','summary')`，无 `card_name = ?`
- `CardDetailView.vue:2256 / 2303`：测卡每次构建 payload 调 `buildMemoryContext(lastUser)`
- 结论：测卡 A 注入测卡 B/C/D 的记忆 → 上下文混乱

### 3.2 检索词过宽，相关性≈0 —— P0

- `MemoryPlugin.java:168-176`：query 按 `[\s,，。.!！?？;；:：、]+` 切词，`content LIKE %词%` OR 连词
- "我喜欢红色的花"切出 `我/喜欢/红色/的/花`，常用字命中每一条 → 实际返回"最近 20 条全卡 fact"
- `MemoryPlugin.java:164-166`：空 query 直接返回最近 N 条
- **`AND ()` 隐含 SQL 错误（待实证标注）**：全标点 query 切词后为空，拼出 `WHERE scope AND ()` → SQL 语法错误 → plugin reject → JS 静默返回 `[]`。**此为代码走查推断的因果链，实施时需先构造全标点 query 实证完整链路（plugin reject → JS 返回空）再确认修复。**
- 因测卡场景用户消息大量为"继续/1/好"等短输入 → 停用词过滤后有效词 <2 的**降级路径会是常态而非兜底**，其 N 值/排序/I2 约束须明确定义（D2 简版）

### 3.3 事实提取误吞整段文本 —— P0

`useChatMemory.js:68-79` 的 8 条启发式正则：

| 规则 | 误命中示例 | 后果 |
|---|---|---|
| 规则6 `我?(?:现在|正在|身处)?(?:在|身处)...` | "**我在**思考怎么解决…" | `位置 = 思考怎么解决…`（整段） |
| 规则8 `我的(.+?)(?:是|为)...` | "**我的想法是**我们应该先…" | `备忘 = 我们应该先…`（一整句） |
| 规则3 `我?...(?:讨厌|不喜欢)...` | "**不喜欢**这种反复测试的感觉" | `讨厌 = 这种反复测试的感觉` |

值无长度上限（`useChatMemory.js:90`），无疑问/否定/假设语气排除 → 长文 fact 原样注入 system

### 3.4 事实无更新、无限膨胀；summary 是死代码 —— P1（D4 提入 P0 后归 P0）

- `MemoryPlugin.java:84-85`：去重要求 `type+content+card_name` 三元一致 → 同 key 不同值每轮新增
- **全仓库无 `recordSummary`/`'summary'` 写入**（grep 证实）→ L2 死代码
- 注入额度（默认 20 条）被同 key 长文事实占满

### 3.5 同名卡/多会话共用记忆 —— P1（定性 + 开关）

- 记忆 key 是 `card.value.name`（显示名，`CardDetailView.vue:2377-2380`）
- **定性**：同卡多会话跨会话共享 = by design（角色连续性），可通过会话级开关（2.0.3）关闭
- **同名卡合并是真实 bug**：显示名相同但内容不同的卡共享记忆 → D1 用 path（唯一标识）分桶，显示名降级为 fallback

### 3.6 记录不准确（L1 层）—— P2

- user 记宏替换+正则处理后的 `processedText`（2356-2377）非原话
- assistant 永远记 `swipes[0]`（2378），切候选/再生成后不回写
- 状态栏 HTML 模板类回复整体入 L1（仅过滤 `⚠` 空串）

## 六、注入格式对比（I4 详设，修正版）

### 6.1 现状（Markdown 表格，效果差）
```markdown
### 记忆表格（角色已记住的信息，请在对话中自然运用，不要逐条复述）
| 记忆 | 内容 |
| --- | --- |
| 名字 | 星野 |
| 喜好 | 红色的花 |
```
表头/分隔行的 token 浪费 + `|` 转义风险 + Claude 对 Markdown 表格识别差。

### 6.2 推荐格式 C（XML + key-value 缩进，P0 默认）
```xml
<memory>
<user_profile>
  名字：星野
  年龄：18岁
  喜好：红色的花
  位置：学校图书馆
  目标：成为漫画家
</user_profile>
<recent_events>
- 星野在图书馆门口遇到主角
- 主角答应帮星野买新画笔
</recent_events>
</memory>
```

### 6.3 格式选择说明（删 overclaim）
- **XML 标签对 Claude 有官方背书**（Anthropic："XML tags help Claude parse complex prompts unambiguously"）
- **对其他模型**：中性偏正、**无官方结论**（不宣称"GPT-4 识别 XML 最佳"）
- **key-value 纯文本是全模型最稳兜底**
- 格式 C 兼具 XML 边界 + key-value 可读，**推荐为默认**；设置页下拉（格式 C / key-value / Markdown）留 P1

### 6.4 实现修正（评审 4 项）
1. **profileKeys 单一常量源**：`useChatMemory.js` 的 FACT_RULES 产出的 key 集合提为常量 `FACT_KEYS`，提取规则（D3）与注入分类（I4）共用——杜绝两处漂移（现状 I4 示例里"喜欢/喜好"并列即漂移征兆）
2. **空记忆守卫**：facts 与 summaries 均空时整体跳过注入（不输出空 `<memory>` 标签）——护栏新增第 6 条
3. **截断先于转义**：80 字符截断在 XML 转义之前，避免 `&lt` 残片
4. **不输出格式 A**（`<name>星野</name>` 以 key 做标签名）——避免非法标签字符风险；格式 A 仅作概念示意，不实现
5. **P0 固定格式 C，无模型类型检测**（字符串匹配 claude/gpt 遇中转端点必误判，砍掉）

## 七、数据迁移与灰度（阻塞件，评审 5.1/5.2）

### 7.1 显示名 → path 迁移决策
- 现状记忆按 `card_name`（显示名）分桶；D1 改为 path
- **一对多歧义**：同名卡多张时，显示名 → path 无法可靠映射
- **决策**：迁移时按"显示名匹配到的卡列表"分情况：
  - 唯一匹配 → 迁移到该卡 path
  - 多卡同名 → **进 legacy 桶（`card_name=显示名` 保留）**，不强制拆散（拆散会造成记忆归属错误）；用户可在 M1 管理 UI 手动清理
  - 无匹配（卡已删）→ 丢弃
- **双写过渡**：D1 上线后新写入用 path，旧记录按上述规则迁移一次；不双写长期并存

### 7.2 schema 版本化迁移
- `memory_items` 表加 `content_hash` 列（D5）+ `(card_name, type)` 索引（D1）
- 用 `PRAGMA user_version` 版本化迁移脚本（对齐 SqliteMetaPlugin 的 SCHEMA_VERSION 模式）
- 迁移脚本在 MemoryPlugin `db()` 初始化时按版本增量执行

### 7.3 灰度开关（feature flag）
- `jsmobile-memory-v2`（localStorage）：关闭时完全走旧路径（旧分桶、旧注入、旧格式）
- 灰度步骤：① 内部/单用户开启 → ② 观察 debug 面板注入质量 + 用户反馈 → ③ 全量开启 → ④ 迁移存量数据 → ⑤ 移除 flag
- 行为变更（D1/D4/I4）+ schema 变更（hash 列）都有退路

## 八、验收标准（修正版）

| 项 | 标准 |

## 十、防新 bug 的护栏

1. **检索隔离只加不减**：注入走 `searchMemory`（加卡过滤），查看器走 `listMemory`（不加），职责分离
2. **fact 规则改动加单测**：新增误命中回归（"我在思考…"应返回空）
3. **停用词表/常量集中可配置**：`FACT_KEYS` 单一常量源（6.4-1）
4. **覆盖更新保持幂等**：同 key 覆盖保留首次 `created_at`，防"每次刷新时间戳排最前"
5. **降级路径**：检索失败/无效词静默降级"当前卡最近 N 条"（N = I2 条数），绝不注入全卡数据
6. **空注入守卫**：无 facts 且无 summaries 时整体跳过注入（6.4-2）
7. **截断先于转义**：避免转义实体残片（6.4-3）
8. **批量抑制保底**：B1 开启时即使写入路径被误调也先查批量状态再写
