# 两万张卡卡库性能方案（评估稿）

> 版本：v1 草案 · 2026-09-17 · 基于仓库 `main-v1.10`（v1.10.24，commit 9c0e3c9）
> 目标：把 SillyTavern 角色卡管理器移动版的卡库规模目标从"千卡"推到"两万卡"，并给出可评估的分阶段路线。

---

## 0. TL;DR

两万卡库的瓶颈不在"二次启动秒开"（缓存先行路径已成立），而在四个地方：

1. **首次/每次冷扫描太慢**：SAF 枚举 + 2 万次 mtime 查询，实测推算 **8~10 分钟**（1994 卡 scan=57s 线性放大）；
2. **内存失控风险**：内存 `_searchText` 不截断（最坏 **>1GB**）+ CJK 逐字倒排索引（数千万 posting，数百 MB）；
3. **缓存整文件全量读写**：`.jskzx_cache.json` 20MB 上限，`JSON.stringify` 全量落盘（6MB 实测写 9s）与 20MB 级 `parse` 是每次启动与保存的隐性税；
4. **每次启动全量 reconcile**：缓存上屏后必然触发全树 scan + 全量替换，2 万卡下从"秒开"退化为"分钟级后台重活"。

推荐组合：**原生枚举批量 Cursor 化（P0 收益最大）+ scan 分块回传 + 内存/索引降量（P0）→ 缓存分片与差异同步（P1）→ SQLite 元数据库 + FTS5（P2，架构演进选项）**。全部改动保留现有 `path|mtime|size` 指纹体系与负缓存等容错基建，不做推倒重来。

## 1. 现状量化：两万卡在现有链路上会发生什么

基于代码审计（`LibraryFsPlugin.java` / `useMobileLibrary.js` / `searchIndex.js` / `CardLibraryView.vue`）与 v1.10.15 实测基线（1994 卡）推算：

| 环节 | 现状实现 | 1994 卡实测 | 两万卡推算 | 判定 |
|---|---|---|---|---|
| 冷扫描（SAF 枚举 + mtime） | `buildRelIndex` DFS + `dir.listFiles()` 每目录一次 + `fillMtimesParallel` 8 线程**每文件一次** `queryLastModified` | scan=57s | **8~10 分钟**（线性放大） | 🔴 不可接受 |
| scan 结果回传 | `JSArray(files)` 整体 resolve（每文件 ~200B） | — | **单次 4MB+** 过桥 | 🟡 大但可控 |
| chara 文本提取 | `readCharaBatch` 24 卡/批，只读 chara 块 | read=20s | 2 万 PNG × ~100KB ≈ **2GB 文本过桥**（834 批） | 🟡 首扫必经，可断点 |
| 二次启动上屏 | 缓存先行 + Worker 重建 + 60/批渐进 | Displayed 2.6s | ~3-5s（20MB 缓存 parse 是新增成本） | 🟢 基本成立 |
| 缓存落盘 | 整文件 `JSON.stringify` 全量写 | cache=9s（6MB） | 20MB 级，**每次保存都触发** | 🔴 高频税 |
| 内存 `_searchText` | 冷扫描不截断（上限 60K/卡），仅缓存写入截断 1.5K | 内存 ~几十 MB | 最坏 **>1GB** | 🔴 崩溃风险 |
| 搜索倒排索引 | CJK 逐字 token + 全字段文本 | 千卡 OK | **数千万 posting、数百 MB**，构建分钟级 | 🔴 不可接受 |
| 列表渲染 | `renderCount` 24 + 触底 +16，增量 push | 1994 卡 publish 14ms | 每批 push 触发 `filteredLibrary` 全量 filter+sort，加载期 ~834 次全库重排 | 🟡 需直通路径 |
| 启动 reconcile | 缓存上屏后必然全树 scan + 全量替换 | 800 卡 scan 5-9s（已不阻塞详情） | 每次启动 8-10 分钟后台重活 | 🔴 不可接受 |

**结论**：现有架构的"轻量条目 + 缓存先行 + 渐进渲染 + 桥线程分流"方向全对，但两万卡把四个量级问题暴露出来——**枚举 IO、内存全量文本、索引规模、整缓存读写**。四个问题可以各自独立治理，不必改架构骨架。

## 2. 开源项目对标（源码级调研，2026-09-17）

本轮对 7 个开源项目做了 GitHub 源码/文档级调研（逐个下载 README、架构文档与关键源码文件核对，而非只看简介）。按"可融入度"排序，结论如下。

### 2.1 Anki —— 大规模卡片存储 / 增量同步 / 搜索下推的行业蓝本（⭐⭐⭐）

Anki 是"1 万到数十万卡"场景的行业标杆，核心设计（`rslib/src/storage/schema11.sql`、`storage/sync.rs`、`search/*.sql`）：

| Anki 设计 | 机制 | 可融入点 |
|---|---|---|
| **USN 版本号增量** | 每行 `usn` 字段，增量同步 = `WHERE usn >= ?` 取待同步记录，比 mtime 精确（同秒多次修改也可辨） | E1 reconcile diff 的版本号参照；P2 DB 内每行 `usn`/`mod` |
| **csum 内容指纹 + 索引** | notes 表带 `csum`（校验和），`ix_notes_csum` 建索引 → 查重/去重走 DB 索引而非全表扫描 | E2 内容指纹入库 + 索引；查重从"全库水合"变"索引比对" |
| **复合索引支撑查询** | `ix_cards_sched ON cards (did, queue, due)` 为调度查询定制 | P2 cards 表复合索引 `(category, mtime)` / `(subfolder, name)` |
| **搜索=解析→构建 SQL** | `parser.rs` 解析查询语法 → `builder.rs` 构建 SQL → 一组**预编译排序 SQL**（`search/*_order.sql`）供浏览器/调度取数，配合 `prepare_cached` | 搜索/排序全下推 SQLite，两万卡内存零负担 |
| **sfld 故意设为 integer** | 排序字段用整数类型实现数值排序 | P2 排序字段类型设计 |

### 2.2 MaterialFiles（zhanghai）—— SAF 大目录高效枚举的现成答案（⭐⭐⭐）

开源 SAF 文件管理器（`provider/document/resolver/DocumentResolver.kt`）对"大目录遍历慢"的解法，正好覆盖本项目 A1：

- **`queryChildren`**：每目录一次 `buildChildDocumentsUriUsingTree` + `query(childrenUri, null, null)` 单次 Cursor 拿全部子项（注释明示 DocumentsUI 的 DocumentsProviderHelper 也这么做，null 投影对性能无碍）。
- **行缓存 `directoryCursorCache`**：列目录时把**每个子项的整行（含 `_ID/_DISPLAY_NAME/_SIZE/_LAST_MODIFIED/_MIME_TYPE/_FLAGS`）转成 `RowCursor` 缓存进内存 `Map<Path, Cursor>`**；后续 `queryDocument` 读属性**命中缓存即返回，零 provider 调用**——彻底消灭"逐文件 mtime query"。
- **`pathDocumentIdCache`**：子项 documentId 一并缓存，构建单个文件 URI 不再递归查找。
- **`EXTRA_LOADING` 等待**：provider 异步加载时 Cursor 带 `EXTRA_LOADING=true`，用 ContentObserver `waitUntilChanged()` 等待加载完成再读，防拿到半空结果。

→ A1 从"每目录一次 query + 仍逐文件补 mtime"升级为 **"每目录一次 query 拿到全部属性 + 行缓存"**，`fillMtimesParallel` 的 2 万次 query **归零**。

### 2.3 Stash —— 后台任务 / 增量扫描 / 哈希分流的工程样板（⭐⭐）

Go + SQLite 的大规模媒体库（`docs/ARCHITECTURE.md`）：

- **后台 Job 系统**（`pkg/job/`）：Scan/Generate/Clean 全部是任务队列中的 job，带**实时进度（订阅推送）与可取消**。
- **增量遍历**：`file.SymWalk` 遍历时按 **mtime 过滤** + `.stashignore` 跳过，非变更文件不处理。
- **哈希分流**：MD5（内容指纹）+ `oshash`（快速大文件哈希，只取头部+尾部）+ phash（感知哈希）；**只在新增/变更文件上计算**。
- **SQLite 工程化**：WAL、1 写 + 10 读连接池、versioned SQL 迁移（pre/post migrate）、BlobStore（封面可存 DB 或文件系统）。
- **复杂过滤下推**：自定义 query builder 生成原生 SQL（含递归 CTE 做层级标签过滤）。

→ 融入：扫描 Job 化（可取消 + 进度）、查重哈希只算新增/变更、P2 迁移系统与过滤下推。

### 2.4 Komga / Calibre —— 元数据库模式的背书（⭐⭐）

SQLite 元数据库 + 文件监听（本地库）+ 定时调度扫描（网络挂载）+ mtime 比对 + 缩略图缓存 + 重复检测。整体为 P2（SQLite 演进）背书；差异：SAF 无 inotify，本项目用 A1 的低成本枚举 + E1 的 diff 逼近"事件驱动"。

### 2.5 MiniSearch —— 现成的内存友好 JS 全文索引（⭐⭐ 替代自研 searchIndex）

纯 JS 全文搜索引擎，README 明示**面向移动浏览器等内存受限场景**：内存高效索引、前缀/模糊匹配、字段加权、**文档可增量 add/remove**、自定义 tokenizer、零依赖。→ C2 可直接替换自研 `searchIndex`（省内存 + 免费获得前缀/模糊/字段加权），中文按自定义 tokenizer（单字/bigram）切分。

### 2.6 sql.js（WASM SQLite）—— 明确的**反例**（结论）

WASM SQLite 把**整个数据库载入内存**、不持久化、需手动 `export()` 整库写盘。两万卡下 DB 20MB+ 全载内存 + 全量落盘，是现架构"整缓存全量读写"问题的放大版。→ **P2 的 SQLite 必须放原生侧**（Android 自带 + 桥接），不在 JS/WebView 侧跑 WASM DB。

### 2.7 虚拟滚动（vue-virtual-scroller / TanStack Virtual）

现列表 `renderCount` 渐进式（24 起 + 16/批）已控住 DOM；只有当两万卡加搜索过滤后频繁重建列表时，才考虑换虚拟滚动。列为备选，不做前置投入。

---

**整体归纳**：外部开源给出的解法收敛为四条主线——①**枚举只做一次**（SAF 批量 query + 行缓存，MaterialFiles）；②**变更靠版本号/指纹**（Anki USN/csum）；③**重活全后台、可取消、带进度**（Stash job 系统）；④**查询/排序/过滤下推数据库**（Anki/Stash/Calibre 共指 SQLite）。四条与本方案 P0/P1/P2 一一对应，见下表：

| 本文档 | 现阶段 | 融入的开源机制 |
|---|---|---|
| A1 枚举改造 | P0 | MaterialFiles `queryChildren` + 行缓存 + `EXTRA_LOADING` 等待 |
| A3/E1 扫描与 diff | P1 | Stash job 化（进度/取消）；Anki USN 版本号思想 |
| E2 查重 | P1 | Anki `csum`+索引；Stash 哈希分流（只算新增/变更） |
| C2 搜索降量 | P0 | MiniSearch（或借鉴其内存结构）替代自研 searchIndex |
| B2 SQLite | P2 | Anki schema（usn/csum/复合索引）+ Stash 迁移系统/连接池 + 预编译排序 SQL；**不采用** sql.js |

**本项目与上述模式的最大差异**：SAF 目录树**没有 inotify/文件系统事件**，无法像桌面媒体库那样事件驱动增量，只能靠"低成本枚举（A1）+ 指纹/版本号 diff（E1/E2）"逼近增量效果。所以 P0 的枚举成本必须打下来，否则每次启动的全量 reconcile 无解。

## 3. 总体架构建议

```
┌─ 前端（现状不动）───────────────────────────────────────┐
│ CardLibraryView / useSearch / searchIndex              │
│   ├─ 改动1: 内存 _searchText 截断（降 1GB → ~30MB）      │
│   ├─ 改动2: 索引降量（关键字段倒排 + 正文降级线性）        │
│   └─ 改动3: 加载期 filter/sort 直通（跳过全库重排）       │
```

## 4. 分项方案

### A. 原生扫描层（P0，收益最大）

**A1. 枚举批量 Cursor 化 + 行缓存（替代逐文件 mtime query；参照 MaterialFiles `queryChildren`）**

- 现状：`buildRelIndex` 每个目录 `dir.listFiles()` 一次 query，然后 `fillMtimesParallel` 对**每个文件**再 `queryLastModified`（2 万卡 = 2 万次 query，实测 1994 卡 scan 的 57s 大头）。
- 改法（对齐 MaterialFiles `DocumentResolver.queryChildren`）：
  1. DFS 每进一个目录，用 `buildChildDocumentsUriUsingTree(treeUri, docId)` + **单次** `contentResolver.query(uri, null, null)`，一次 Cursor 同时拿全部子项的 `_ID / _DISPLAY_NAME / _SIZE / _LAST_MODIFIED / _MIME_TYPE / _FLAGS`（null 投影与 DocumentsUI 同款，性能无碍）；
  2. **行缓存**：把每个子项所在行转成 `RowCursor` 存入 `Map<relPath, Cursor>`，扫描输出的 mtime/size 直接来自缓存，`fillMtimesParallel` **整个删除**（2 万 query → 0）；
  3. documentId 一并缓存（`path→documentId`），后续单文件读写/移动/删除免递归解析；
  4. Cursor 带 `EXTRA_LOADING` 时用 ContentObserver `waitUntilChanged()` 等 provider 异步加载完成再消费，防拿到半空列表。
- 量级：若 2 万卡分布在 ~200 个子目录，query 次数从 **2 万次 → ~200 次**；枚举总成本主要变成 provider 端递归，真机预计 scan 从 8-10 分钟压到 **1-3 分钟**量级（provider 行为决定，需真机测）。
- 兼容：个别 provider 不支持某列时该列返回 null，按缺省值处理；`DocumentFile` 仅保留在 write 侧（已有）。
- 保留：隐藏目录跳过、`SKIP_FOLDERS`、`isTransientFile` 三种 tmp 过滤逻辑原样迁移。

**A2. scan 结果分块回传（消灭 4MB 单次 resolve）**

- 现状：`JSArray(files)` 整体 resolve，Capacitor 通过 `evaluateJavascript` 注入大字符串，主线程一次性 parse 2 万条。
- 改法：新增游标协议 `scanOpen / scanNext(batchSize=500)`（或 `notifyListeners` 分块推送），JS 侧逐块接收、逐块合并到本地列表。单块 < 500KB。
- 收益：与"扫描进行中即可浏览"结合（见 E1），用户首块即可看到卡，不再等 4MB 全部落地。

**A3. 扫描 checkpoint（断点续扫）**

- 现状：首次冷扫描中途杀掉进程，下次从头再扫（2 万卡反复 10 分钟）。
- 改法：原生侧（或缓存文件内）记录 `{ 已扫描的目录路径集合, 进度 }`，重启后从断点继续枚举；配合 A1 的低成本枚举，断点记录可以很粗（每目录一行）。

### B. 缓存层（P1 分片 → P2 SQLite 演进）

**B1. P1：缓存分片 + 增量写**

- 现状：单文件 `.jskzx_cache.json`（上限 20000 条 ~20MB），`scheduleCacheFlush` 整文件 `JSON.stringify`（6MB 写 9s），`restoreViaWorker` 还要先 `JSON.stringify(cache)` 再过桥（20MB 级重复序列化）。
- 改法：
  - 拆为 `.jskzx_cache/` 目录 + 按路径哈希前缀分片（如 16 片 `00.json ~ 0f.json`），**单卡变更只重写所在分片**（每片 ≤1.25MB）；
  - restore 时 Worker 并行读分片（或原生侧按片读取）；
  - 去掉 `restoreViaWorker` 里的重复 `JSON.stringify`（直接传文本，或干脆分片后按需读）。
- 收益：保存链路从"20MB 全量写"→"1.25MB 单片写"；恢复从"20MB 一次 parse"→"16 片并行 parse"。
- 保留：指纹键、`evictSamePathCache`、负缓存、按 path 去重、20000 条上限全部原样（上限改按分片内裁剪）。

**B2. P2（可选演进）：SQLite 元数据库（Calibre/Komga/Anki 共识架构）**

- 若 P1 后仍需更强查询/比对，将缓存演进为 SQLite。schema 借鉴 Anki（`rslib/storage/schema11.sql`）：

  ```sql
  CREATE TABLE cards (
    path TEXT PRIMARY KEY,            -- 相对库根路径（Anki/Calibre 存相对路径，防整库搬移失效）
    name TEXT, creator TEXT, desc TEXT,
    tags TEXT, subfolder TEXT, category TEXT,
    tokens INTEGER, flags INTEGER,
    mtime INTEGER, size INTEGER,
    csum INTEGER,                     -- 内容轻量指纹（Anki ix_notes_csum 同款，查重/去重走索引）
    usn  INTEGER,                      -- 变更版本号（Anki USN：增量 reconcile / 后续同步）
    indexed_at INTEGER
  );
  CREATE INDEX ix_cards_mtime ON cards (mtime, size);
  CREATE INDEX ix_cards_csum  ON cards (csum);
  CREATE INDEX ix_cards_cat  ON cards (category, name);   -- 复合索引，Anki ix_cards_sched 同思路
  ```

- **工程化（Stash 模式）**：WAL + 1 写/多读连接池；versioned SQL 迁移（pre/post migrate）管理 schema 升级；封面等二进制可存 `BlobStore`（DB 或文件系统，参照 Stash）。
- **搜索/排序下推（Anki parser→builder→SQL 模式）**：查询语法在 JS 解析为过滤条件，原生按需生成 SQL + 预编译排序 SQL（`ORDER BY` 变体），两万卡排序/分页零内存负担；复杂标签过滤用递归 CTE（Stash criterion handler 同款）。
- **中文搜索**：Android 系统 SQLite 版本因厂商而异，**FTS5 trigram 不保证可用**；稳妥做法是预分词字段（空格分隔的词/单字 + 词组）+ `simple` tokenizer，或对 CJK 做双字（bigram）切分；备选是维持内存索引只存关键字段（见 C2）。
- **明确排除**：WASM SQLite（sql.js）——整库载内存 + export 全量写盘，两万卡下是现"整缓存全量读写"问题的放大版；SQLite 必须在原生侧经桥接暴露（新增 `dbExec/dbQuery`，JS 沿用 `electronAPI` 语义封装）。
- 收益：reconcile diff 下推 DB（`SELECT path, mtime, size, usn` 一次对比）、排序分页下推、查重签名存表增量维护、删索引不必全量重排。
- 成本：改动面最大（原生 + 桥 + JS 数据层），建议 P2 单独评估立项，**不阻塞 P0/P1 落地**。

### C. 内存与搜索层（P0，两颗雷必须拆）

**C1. 内存 `_searchText` 截断**

- 现状：`cardLight.js` 只在**写缓存时**截断 1.5K；内存条目（冷扫描路径）保留上限 60K 全文 → 两万卡最坏 >1GB。
- 改法：内存条目与缓存一致截断（1.5K，两万卡 ~30MB，可接受；或折中 4K ~80MB）。
- 权衡（写清楚，供评估）：截断后超长 description 的**尾部**无法命中全文搜索；两万卡场景下这是合理取舍——真正要全文检索时走 P2 FTS5。**此改动立即消除最确定的崩溃风险**，建议 P0 第一个做。

**C2. 搜索索引降量（候选：MiniSearch 替代自研 searchIndex）**

- 现状：`searchIndex` CJK 逐字 token 化全字段 `_searchText`，两万卡 = 数千万 posting、数百 MB、分钟级构建；且 `_getMatches` 在未命中时线性遍历全部词表。
- 改法（短期）：
  - **只对短字段建倒排**：`name / creator / tags / fileName` 逐字 token（字段短，posting 可控）；
  - **长文本（description 等，已截断 1.5K）降级为候选集内的线性匹配**（2 万 × 1.5K ≈ 30MB，单次扫描 ~50-100ms，配合 300ms 防抖可接受）；
  - `tag:/author:/file:/wb:` 语法走字段级过滤，不进索引。
- **候选替换**：直接用 **MiniSearch**（开源、面向移动内存受限场景、零依赖、支持增量 add/remove 与字段加权、tokenizer 可自定义）替代自研 `searchIndex`；两万卡下其内存结构远优于逐字 Map，白得前缀/模糊匹配。落地时对比两个实现的内存与耗时再定。
- 量级：posting 从数千万 → 百万级以内，内存数百 MB → 几十 MB。
- 备选：若坚持全字段倒排，改 bigram 分词替代逐字（posting 减半但仍有数千万），不推荐，短期方案已足够。

**C3. 排序/过滤降本**

- 现状：`filteredLibrary` computed 每次全量 `filter + sortList`（2 万卡一次排序 ~28 万次比较），加载期每批 push 都重算。
- 改法：
  - **加载期直通**：`mobileLibrary.loading` 为真时跳过 filter/sort，列表直接渲染增量批次（加载完成才建索引）；
  - 搜索结果只排**候选集**（索引命中后通常远小于 2 万）；
  - reconcile 结束后不再 `library = staging` 全量替换，改**按 path 集合 diff**：本地 Map `path→index`，对新增 push、删除 splice、修改回填，保留数组引用稳定（避免全库重排）。

### D. 渲染层（P0 少量改动）

- 现状 `renderCount` 24 + 触底 +16 已能控制 DOM 规模，保持不动。
- 配合 C3 的加载期直通后，加载期不再有全量 filter/sort 的卡顿；滚动期 `filtered` 只在用户输入/分组/排序变化时重算。

### E. 增量与一致性（P1）

**E1. 启动 reconcile 降级为"低成本枚举 + 版本号 diff"（参照 Anki USN / Stash job 系统）**

- 现状：缓存上屏后必然 `rescanLibrary` 全量 scan（两万卡 = 每次启动 8-10 分钟重活，即使后台跑也消耗电量与 SAF）。
- 改法（依赖 A1）：
  - 枚举成本降下来后，`reconcile` 在原生侧**与上次 scan 快照比对**（原生维护 `path→mtime` 快照或查 DB），只回传 **变更集**（新增/删除/修改路径）；
  - **版本号增量（Anki USN 思想）**：DB/快照中每行记录一个递增版本号，每次 reconcile 后对变更行 +1；增量取数用 `version >= ?`，比 mtime 更精确（同秒多次改动也能识别）；
  - JS 侧只处理变更路径：新增卡走现有 `appendImportedCards` 式批量解析，删除卡从库移除，修改卡按指纹重解析；
  - **扫描 Job 化（Stash 模式）**：扫描作为可取消的后台任务，带实时进度（沿用现有 `progress.done/total` + 通知），可取消/可中断；用户浏览/点详情不受影响（BUG-14 已建立的分流继续生效）。
- 断点：结合 A3，首次冷扫描也可中途退出，下次续扫。

**E2. 查重（内容指纹）增量持久化（参照 Anki `csum` / Stash 哈希分流）**

- 现状：`DedupeModal` 每次全量 `loadCardsFullDataBatch` 水合全部卡算 MinHash/LSH（两万卡 = 2GB chara 过桥 + 分钟级）。
- 改法：
  - 把每卡的**内容签名（96 路 MinHash）持久化**到缓存条目（新增 `sig` 字段或独立表），增量只对"新增/修改卡"重算签名——**哈希只在变更文件上计算（Stash 原则）**；
  - 轻量内容指纹（Anki `csum` 思想）：`description/personality/scenario/first_mes` 拼接后算一个短校验和（如 xxHash/MD5 截断）入库并建索引，同名/同内容卡先按 `csum` 快速分组，再对组内卡做 MinHash 相似度确认（LSH 分桶与 Union-Find 聚类逻辑不变）；
  - 二次查重 = 读持久化签名 + 只聚类增量，从分钟级变秒级；首查仍是一次性成本但可用 Stash 式后台 Job 跑（可取消 + 进度）。
- 收益：两万卡首查仍然久（一次性成本），但**二次查重是秒级**。

### F. 缩略图（P1）

- 现状：`THUMB_MAX_CACHE=1500`，滚动两万卡时生成-淘汰循环打满线程池。
- 改法：磁盘缓存上限改为**总容量制**（如 200MB）而非条数；滚动预取用"方向 + 视口外 N 屏"批量 `readThumbBatch`（当前仅首屏 60 预热）；淘汰策略保持 LRU。

## 7. 风险与备选

| 风险 | 说明 | 缓解 |
|---|---|---|
| 厂商 DocumentsProvider 对批量 query 支持参差 | 投影/排序列可能被忽略或报错 | 不投影降级路径；`_LAST_MODIFIED` 缺失时回退逐文件 query（仅缺失 provider） |
| SAF 无事件通知，diff 仍需枚举 | 枚举成本已由 A1 压到分钟级以下，但每次启动仍有一次全树枚举 | 原生侧快照比对只在枚举后做内存 diff；枚举本身后台低优先级 |
| FTS5 中文（trigram）在旧 Android SQLite 不可用 | API 24 系统 SQLite 版本因厂商而异 | P2 采用预分词字段 + simple tokenizer；或维持 C2 内存方案 |
| SQLite 引入推高改动面 | 原生 + 桥 + JS 数据层三处 | P2 独立立项，P0/P1 不依赖它 |
| 截断后的全文搜索语义变化 | 超长 description 尾部搜不到 | 明确取舍；P2 FTS5 兜底全文 |
| WebView 大字符串解析 | scan 4MB 单次回传已存在 | A2 分块协议，每块 <500KB |
