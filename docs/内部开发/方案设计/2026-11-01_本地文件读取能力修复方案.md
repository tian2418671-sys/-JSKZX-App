# 方案：本地文件读取能力「斩草除根」修复（OPPO 等机型读不到文件 / 找不到位置）

> 日期：2026-11-01 · 目标版本：v1.10.33（未发布）· 状态：待上游评审
> 适用仓库：`JSK管理APP`（移动端）+ 结论同步桌面版

## 0. 一句话结论

当前 App 的文件访问只有 **SAF 一条腿**，而 SAF 的行为完全依赖设备上的 DocumentsProvider 与 DocumentsUI。
只要其中一个环节在某个 ROM 上不按 AOSP 走（OPPO/ColorOS 已知），用户就会得到「找不到位置」或「读不到文件」，
且**没有任何第二通道可以兜底**。本方案做两件事：

1. **把 SAF 这条腿接稳**（选择器定位、授权持久化、异步 provider 等待、主线程阻塞）；
2. **补上第二条腿**（`MANAGE_EXTERNAL_STORAGE` 路径级访问 + App 内目录浏览器），使「找不到位置/读不到文件」在**任何** ROM 上都有解。

不做：推送到酒馆、分享导入、Shizuku、root —— 这些都不是"文件访问能力"，是旁路。

---

## 1. 问题建模：能力链四段，任一段断掉即"读不到"

```text
① 定位            ② 授权持久化        ③ 枚举                ④ 读取
选择器能否打开     重启后授权还在吗     provider 是否给全量    路径→文件能否解析
到用户想去的目录                       （异步加载/列/缺列）
```

用户报的两种症状与本链的对应关系：

| 症状 | 断在哪一段 | 代码位置 |
| --- | --- | --- |
| 找不到位置（选择器空白/停在"最近"/进不去目录） | ① | `putInitialDownloadsUri()` |
| 上次好好的，这次"库目录已失效" | ② | `pickFolderResult()` / `pickPushFolderResult()` |
| 授权成功但「扫描到 0 张」/ 数量偏少 | ③ | `buildRelIndex()` / `scanWbTree()` / `scanFolderResult()` |
| 列表有卡，点开读不出内容 | ④ | `fileByRelPath()` / `readBuffer()` 异常路径 |
| ROM 上 SAF 整体不可用 | 无通道 | **缺 P1 兜底** |

---

## 2. 现状证据与补丁（P0：把 SAF 这条腿接稳）

### 2.1【①定位】`EXTRA_INITIAL_URI` 传了非法的 URI 类型

**现状代码** `android/app/src/main/java/com/sillytavern/cardmanager/android/LibraryFsPlugin.java:483`

```java
    private void putInitialDownloadsUri(Intent intent) {
        try {
            Uri initial = null;
            if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q) {
                initial = MediaStore.Downloads.EXTERNAL_CONTENT_URI;
            } else {
                File dl = Environment.getExternalStoragePublicDirectory(Environment.DIRECTORY_DOWNLOADS);
                if (dl != null) initial = Uri.fromFile(dl);
            }
            if (initial != null) {
                intent.putExtra(DocumentsContract.EXTRA_INITIAL_URI, initial);
            }
        } catch (Throwable t) {
            // 某些设备不支持初始目录,回退默认选择器
        }
    }
```

**根因**：`DocumentsContract.EXTRA_INITIAL_URI` 要求 **DocumentsProvider 的 document URI**
（`content://<documents authority>/document/<docId>`），而 `MediaStore.Downloads.EXTERNAL_CONTENT_URI`
是 `content://media/external/downloads` —— 属于 MediaStore 域，不是文档域。
AOSP DocumentsUI 会静默忽略，部分国产 ROM 的选择器会因此停在「最近」或空白页（用户即「找不到位置」）。
且没有任何校验：即使 provider 根本解析不了，也照样塞进去。

#### 补丁：初始 URI 合法化 + 可解析校验

```java
    /** DocumentsUI 的 EXTRA_INITIAL_URI 必须是 DocumentsProvider 的 document URI(不是 MediaStore 媒体 URI) */
    private void putInitialDownloadsUri(Intent intent) {
        try {
            Uri initial = null;
            if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q) {
                Uri candidate = DocumentsContract.buildDocumentUri(
                        "com.android.externalstorage.documents", "primary:Download");
                if (canResolveDocument(candidate)) initial = candidate;   // 解析不了就不设,等价默认定位
            } else {
                File dl = Environment.getExternalStoragePublicDirectory(Environment.DIRECTORY_DOWNLOADS);
                if (dl != null) initial = Uri.fromFile(dl);
            }
            if (initial != null) intent.putExtra(DocumentsContract.EXTRA_INITIAL_URI, initial);
        } catch (Throwable t) {
            // 保持默认定位,不阻断选择器
        }
    }

    /** provider 是否真能解析该 document URI(避免把打不开的位置交给选择器) */
    private boolean canResolveDocument(Uri docUri) {
        try (android.database.Cursor c = getContext().getContentResolver().query(
                docUri, new String[]{ DocumentsContract.Document.COLUMN_DOCUMENT_ID }, null, null, null)) {
            return c != null && c.getCount() > 0;
        } catch (Exception e) {
            return false;
        }
    }
```

**风险**：若设备无 `com.android.externalstorage.documents`，`canResolveDocument` 返回 false → 不设 extra → 等价旧版兜底，不会更差。
**验收**：OPPO/小米/原生 三台机器上点「选择库目录」，选择器直接打开在 Download 且可继续导航；若该 ROM 不支持，则正常打开根列表（不得空白）。

### 2.2【②授权持久化】硬编码 flags + 静默吞异常 → 重启后失效

**现状代码** `LibraryFsPlugin.java:540`

```java
    @com.getcapacitor.annotation.ActivityCallback
    private void pickFolderResult(PluginCall call, ActivityResult result) {
        if (result == null || result.getResultCode() != android.app.Activity.RESULT_OK
                || result.getData() == null) {
            call.reject("用户取消选择");
            return;
        }
        Uri uri = result.getData().getData();
        if (uri == null) {
            call.reject("未获取到目录");
            return;
        }
        // 持久化授权(重启后仍可访问)
        try {
            getContext().getContentResolver().takePersistableUriPermission(uri,
                    Intent.FLAG_GRANT_READ_URI_PERMISSION | Intent.FLAG_GRANT_WRITE_URI_PERMISSION);
        } catch (SecurityException e) {
            // 部分文件管理器不返回可持久化授权,忽略即可(本次会话仍可用)
        }
        setRootUri(uri);
        JSObject ret = new JSObject();
        ret.put("success", true);
        ret.put("uri", uri.toString());
        call.resolve(ret);
    }
```

**根因**（三处叠加）：

1. `takePersistableUriPermission` 的第二个参数必须来自 `result.getData().getFlags()`
   **按位与**的结果；这里硬编码了 `READ|WRITE`。若选择器只授予读权限，写入调用会抛
   `SecurityException` → 整次持久化**全部失败**（一点没存下）。
2. 未检查 `Intent.FLAG_GRANT_PERSISTABLE_URI_PERMISSION`：不可持久化的 provider 上，任何调用都必然失败。
3. 异常被静默吞掉，JS 侧只拿到 `success:true` → 用户当场能用、**重启后库目录失效**
   （正是测试清单 6.2 要覆盖的场景，但当前实现无法区分"应用失败"与"ROM 不支持"）。

#### 补丁：按实际 flags 持久化并回传

```java
    /**
     * 按选择器实际授予的 flags 持久化授权。
     * 返回 {persisted, takeFlags} —— 失败必须回传,不能静默(否则重启后用户只会看到"库目录已失效")。
     */
    private boolean tryPersist(Uri uri, Intent data) {
        int flags = (data != null) ? data.getFlags() : 0;
        if ((flags & Intent.FLAG_GRANT_PERSISTABLE_URI_PERMISSION) == 0) return false; // provider 不支持持久化
        int take = flags & (Intent.FLAG_GRANT_READ_URI_PERMISSION | Intent.FLAG_GRANT_WRITE_URI_PERMISSION);
        if (take == 0) take = Intent.FLAG_GRANT_READ_URI_PERMISSION;
        try {
            getContext().getContentResolver().takePersistableUriPermission(uri, take);
            return true;
        } catch (SecurityException e) {
            android.util.Log.w("Perf", "takePersistableUriPermission failed: " + e.getMessage());
            return false;
        }
    }

    @com.getcapacitor.annotation.ActivityCallback
    private void pickFolderResult(PluginCall call, ActivityResult result) {
        if (result == null || result.getResultCode() != android.app.Activity.RESULT_OK
                || result.getData() == null) {
            call.reject("用户取消选择");
            return;
        }
        Intent data = result.getData();
        Uri uri = data.getData();
        if (uri == null) {
            call.reject("未获取到目录");
            return;
        }
        boolean persisted = tryPersist(uri, data);
        setRootUri(uri);

        // 诊断回传:真机问题一次说清,不再靠猜
        DocumentFile root = DocumentFile.fromTreeUri(getContext(), uri);
        JSObject ret = new JSObject();
        ret.put("success", true);
        ret.put("uri", uri.toString());
        ret.put("persisted", persisted);
        ret.put("provider", uri.getAuthority());
        ret.put("canRead", root != null && root.canRead());
        ret.put("canWrite", root != null && root.canWrite());
        try {
            ret.put("rootId", DocumentsContract.getTreeDocumentId(uri));
        } catch (Exception e) {
            ret.put("rootId", "");
        }
        call.resolve(ret);
    }
```

`pickPushFolderResult()`（`:602`）同样替换为 `tryPersist(uri, data)`，并在返回值中带上 `persisted`。

**风险**：返回值新增字段，属**向后兼容**（JS 读取可选字段）。
**验收**：授权 → 杀进程 → 重启 → 库正常加载；对不可持久化授权的 provider，UI 明确提示"本次可用，重启后需重新选择"，而不是静默。

### 2.3【③枚举】provider 异步加载未等待 → 拿到半空列表

**现状代码** `LibraryFsPlugin.java:153`（方法起点；子项查询在 `:179`）

```java
                cursor = getContext().getContentResolver().query(childrenUri, DOC_CHILD_PROJECTION, null, null, null);
                if (cursor == null) throw new IllegalStateException("children 查询返回空游标");
                int idxId   = cursor.getColumnIndex(DocumentsContract.Document.COLUMN_DOCUMENT_ID);
                ...
                while (cursor.moveToNext()) { rowsSeen++; ... }
```

**根因**：`DocumentsProvider` 可以**异步**返回子项 —— Cursor 的 extras 里带
`DocumentsContract.EXTRA_LOADING=true`，此时行数是不完整的。直接消费 = 列表缺项/为空。
本仓库 [方案设计/两万卡卡库性能方案.md](../方案设计/两万卡卡库性能方案.md) 第 64 行与第 149 行**已写明**
MaterialFiles 用 `ContentObserver.waitUntilChanged()` 等待该标志，但代码中 grep 不到任何
`EXTRA_LOADING` / `ContentObserver` —— 方案从未落地。OPPO 上 provider 加载慢，此窗口被放大。

#### 补丁：provider 异步加载等待

```java
    /**
     * 带 EXTRA_LOADING 等待的子项查询:
     * provider 异步加载时会先返回一个「行还没齐」的 Cursor,必须等它 notifyChange 后再重新查询。
     * 超时兜底(默认 1500ms),最坏情况等价于现状,不会更差。
     * ⚠ 必须运行在后台线程(SCAN_EXEC),不得在主线程调用。
     */
    private android.database.Cursor queryChildrenSettled(Uri childrenUri, long timeoutMs) {
        final android.content.ContentResolver cr = getContext().getContentResolver();
        android.database.Cursor c = cr.query(childrenUri, DOC_CHILD_PROJECTION, null, null, null);
        if (c == null) return null;
        boolean loading = false;
        try {
            android.os.Bundle extras = c.getExtras();
            loading = extras != null && extras.getBoolean(DocumentsContract.EXTRA_LOADING, false);
        } catch (Exception ignored) { /* 部分 provider 不提供 extras */ }
        if (!loading) return c;

        final java.util.concurrent.CountDownLatch latch = new java.util.concurrent.CountDownLatch(1);
        android.database.ContentObserver observer = new android.database.ContentObserver(
                new android.os.Handler(android.os.Looper.getMainLooper())) {
            @Override public void onChange(boolean selfChange) { latch.countDown(); }
        };
        cr.registerContentObserver(childrenUri, true, observer);
        try {
            if (!latch.await(timeoutMs, java.util.concurrent.TimeUnit.MILLISECONDS)) {
                android.util.Log.w("Perf", "EXTRA_LOADING timeout: " + childrenUri);
            }
        } catch (InterruptedException ignored) {
        } finally {
            try { cr.unregisterContentObserver(observer); } catch (Exception ignored) { }
        }
        try { c.close(); } catch (Exception ignored) { }
        return cr.query(childrenUri, DOC_CHILD_PROJECTION, null, null, null); // 重开以拿到补全后的行
    }
```

接入点（`buildRelIndex()` 内）：

```java
-                cursor = getContext().getContentResolver().query(childrenUri, DOC_CHILD_PROJECTION, null, null, null);
+                cursor = queryChildrenSettled(childrenUri, 1500L);
                 if (cursor == null) throw new IllegalStateException("children 查询返回空游标");
```

`scanWbTree()`（`:2320`）内的 `dir.listFiles()` 亦改为经 `queryChildrenSettled` 枚举（DocumentFile 内部同样是 children 查询，无法等待）。

**风险**：每目录最坏多 1.5s（仅当 provider 明确报告 loading 时）。万卡库若命中大量异步目录会拖慢首扫 → 因此时限用 1500ms 且仅对该标志生效。
**验收**：对异步 provider（模拟器可用自建 DocumentsProvider 或把目录放到云端 provider）扫描，行数完整；AOSP 本地 provider 无额外耗时（`EXTRA_LOADING` 不出现）。

### 2.4【③枚举】`scanFolderResult` 在主线程遍历整棵树

**现状代码** `LibraryFsPlugin.java:1894`（`scanFolder`）/ `:1903`（`scanFolderResult`，磁盘扫描）

```java
    @PluginMethod()
    public void scanFolder(final PluginCall call) {
        Intent intent = new Intent(Intent.ACTION_OPEN_DOCUMENT_TREE);
        putInitialDownloadsUri(intent);
        intent.putExtra("__ext", call.getString("ext", ".png"));
        intent.putExtra("__skipLarge", call.getBoolean("skipLarge", true));
        startActivityForResult(call, intent, "scanFolderResult");
    }

    @com.getcapacitor.annotation.ActivityCallback
    private void scanFolderResult(PluginCall call, ActivityResult result) {
        ...
        DocumentFile root = DocumentFile.fromTreeUri(getContext(), treeUri);
        ...
        while (!stack.isEmpty()) {
            DocumentFile dir = stack.pop();
            DocumentFile[] children = dir.listFiles();     // ← 主线程逐目录 SAF IPC
            ...
        }
```

**根因**：`@ActivityCallback` 在 **主线程** 回调。整棵树递归 + 每个目录一次 SAF IPC 全部压在主线程：
大目录下必然触发 ANR/被系统杀掉（ColorOS 的 watchdog 更激进），用户看到的是"扫描失败 / 卡住 / 读不到"。
这与 BUG-14「重活不许占桥线程」是同一类问题，但此处连后台线程都没进。

#### 补丁：遍历移出主线程

```java
    @com.getcapacitor.annotation.ActivityCallback
    private void scanFolderResult(PluginCall call, ActivityResult result) {
        if (result == null || result.getResultCode() != android.app.Activity.RESULT_OK || result.getData() == null) {
            call.reject("用户取消选择目录");
            return;
        }
        final Uri treeUri = result.getData().getData();
        if (treeUri == null) { call.reject("未获取到目录授权"); return; }
        final String ext = call.getString("ext", ".png").toLowerCase(Locale.ROOT);
        final boolean skipLarge = call.getBoolean("skipLarge", true);
        // 整段遍历移出主线程(与 scan/scanStart 共用 SCAN_EXEC)
        SCAN_EXEC.execute(() -> {
            try {
                ... 原 while 遍历逻辑(改用 queryChildrenSettled) ...
                call.resolve(ret);
            } catch (Exception e) {
                call.reject("扫描失败: " + e.getMessage());
            }
        });
    }
```

**风险**：低（与既有 `scan`/`scanStart` 同款模式）。
**验收**：选一个 3000+ 文件的目录扫描，UI 不冻结、进度事件持续、无 ANR；真机 OPPO 上同样成立。

### 2.5【④读取】授权有效性判断只靠 `root.exists()`

**现状代码** `LibraryFsPlugin.java:567`

```java
    @PluginMethod()
    public void libraryInfo(PluginCall call) {
        String uriStr = prefs().getString(KEY_ROOT_URI, null);
        DocumentFile root = (uriStr != null) ? DocumentFile.fromTreeUri(getContext(), Uri.parse(uriStr)) : null;
        JSObject ret = new JSObject();
        ret.put("granted", root != null && root.exists());
        ret.put("hasUri", uriStr != null);
        ret.put("uri", uriStr);
        call.resolve(ret);
    }
```

**根因**：`exists()` 失败时返回 false，但 **既区分不了「授权被回收」与「provider 暂时读不到」**，
也无法告诉前端"当前是 SAF 后端还是路径后端"。后续引入 P1 双后端时这是必要字段。

#### 补丁：授权有效性判断与后端字段

```java
    @PluginMethod()
    public void libraryInfo(PluginCall call) {
        String uriStr = prefs().getString(KEY_ROOT_URI, null);
        String pathStr = prefs().getString(KEY_ROOT_PATH, null);   // P1 新增
        JSObject ret = new JSObject();
        ret.put("hasUri", uriStr != null);
        ret.put("uri", uriStr);
        ret.put("path", pathStr);
        if (pathStr != null && !pathStr.isEmpty()) {               // 路径后端优先
            File f = new File(pathStr);
            ret.put("backend", "path");
            ret.put("granted", f.isDirectory() && f.canRead());
            ret.put("uri", uriStr == null ? "" : uriStr);
            call.resolve(ret);
            return;
        }
        boolean granted = false;
        String reason = "";
        if (uriStr != null) {
            try {
                DocumentFile root = DocumentFile.fromTreeUri(getContext(), Uri.parse(uriStr));
                granted = root != null && root.canRead();
                if (!granted) reason = "授权不可读(可能已被系统回收或目录被移动)";
            } catch (Exception e) {
                reason = "授权 URI 无效: " + e.getMessage();
            }
        } else {
            reason = "尚未授权";
        }
        ret.put("backend", "saf");
        ret.put("granted", granted);
        ret.put("reason", reason);
        call.resolve(ret);
    }
```

**验收**：撤销授权后设置页显示"授权不可读(…)"而不是笼统的"已失效"；正常状态 `granted:true, backend:"saf"`。

## 3. P1：补上第二条腿（路径级访问 + App 内目录浏览器）

> 这是"斩草除根"的核心：SAF 在某个 ROM 上怎么坏都不重要，用户永远有第二条能用的通道。

### 3.1 权限与声明

`android/app/src/main/AndroidManifest.xml`

```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:tools="http://schemas.android.com/tools">
    ...
    <!-- 全盘模式:仅当用户在 App 内显式开启时才引导授权;SAF 仍是默认路径 -->
    <uses-permission android:name="android.permission.MANAGE_EXTERNAL_STORAGE"
        tools:ignore="ScopedStorage" />
```

### 3.2 原生接口（新增 4 个方法）

```java
    // endregion

    // region 全盘模式(路径级后端) —— SAF 不可用机型 / 用户想直接按路径浏览时使用
    private static final String KEY_ROOT_PATH = "root_path";

    @PluginMethod
    public void allFilesAccessState(PluginCall call) {
        JSObject ret = new JSObject();
        boolean granted = Build.VERSION.SDK_INT >= Build.VERSION_CODES.R
                && Environment.isExternalStorageManager();
        ret.put("granted", granted);
        ret.put("supported", Build.VERSION.SDK_INT >= Build.VERSION_CODES.R);
        call.resolve(ret);
    }

    @PluginMethod
    public void requestAllFilesAccess(PluginCall call) {
        if (Build.VERSION.SDK_INT < Build.VERSION_CODES.R) { call.reject("系统版本不支持(需 Android 11+)"); return; }
        try {
            Intent i = new Intent(android.provider.Settings.ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION);
            i.setData(Uri.parse("package:" + getContext().getPackageName()));
            getContext().startActivity(i);
            call.resolve(new JSObject().put("success", true));
        } catch (Exception e) {
            call.reject("无法打开系统设置: " + e.getMessage());
        }
    }

    /** 路径级列目录:内部存储 / SD 卡 / U 盘。返回 {path,name,isDirectory,size,mtime} */
    @PluginMethod
    public void listDirByPath(PluginCall call) {
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.R && !Environment.isExternalStorageManager()) {
            call.reject("未授予「所有文件访问权限」");
            return;
        }
        File dir = new File(call.getString("path", Environment.getExternalStorageDirectory().getAbsolutePath()));
        File[] children = dir.listFiles();
        if (children == null) { call.reject("目录不可读"); return; }
        JSArray out = new JSArray();
        for (File f : children) {
            if (f.getName().startsWith(".")) continue;
            JSObject o = new JSObject();
            o.put("path", f.getAbsolutePath());
            o.put("name", f.getName());
            o.put("isDirectory", f.isDirectory());
            o.put("size", f.isFile() ? f.length() : 0L);
            o.put("mtime", f.lastModified());
            out.put(o);
        }
        call.resolve(new JSObject().put("success", true).put("files", out)
                .put("path", dir.getAbsolutePath()));
    }

    /** 以路径作为库根(与 SAF 库根二选一,写入即切换后端) */
    @PluginMethod
    public void setLibraryRootPath(PluginCall call) {
        String path = call.getString("path", "");
        File dir = new File(path);
        if (!dir.isDirectory() || !dir.canRead()) { call.reject("目录不可读"); return; }
        prefs().edit().putString(KEY_ROOT_PATH, dir.getAbsolutePath()).remove(KEY_ROOT_URI).apply();
        relIndexReady = false;
        call.resolve(new JSObject().put("success", true).put("path", dir.getAbsolutePath()));
    }
    // endregion
```

**关键约束（必须写进评审）**：路径后端**同样读不到** `Android/data`、`Android/obb` ——
这是系统限制（官方文档明确「所有文件访问权限」也排除），不是本方案能解决的。
除此之外（内部存储任意目录、SD 卡、U 盘、`Android/media`）路径后端全部可读，且**不依赖任何 provider**。

### 3.3 渲染层接线（不改变对外语义）

`js/bridge/android.js`：`selectFolder()` 增加兜底分支——SAF 选择器失败（拒绝/取消/授权不可读）时，
提示并引导到「全盘模式」：

```js
    async selectFolder() {
        const res = await LibraryFs.pickFolder();
        if (res && res.error) {
            // 不再吞掉:把"为什么失败"交给 UI,并提示可用全盘模式兜底
            return { folderPath: null, files: [], error: res.error, persisted: res.persisted !== false };
        }
        return this.rescanLibrary(LIBRARY_ROOT);
    },
```

新增两个薄封装（`api.js` / `contract.js` 同步登记）：

```js
    async allFilesAccessState() { return await LibraryFs.allFilesAccessState(); },
    async listDirByPath(path) { return await LibraryFs.listDirByPath({ path }); },
    async setLibraryRootPath(path) {
        const r = await LibraryFs.setLibraryRootPath({ path });
        return r && r.success ? this.rescanLibrary(LIBRARY_ROOT) : { files: [], error: (r && r.error) || '切换失败' };
    },
```

UI：设置页新增「全盘模式」分组（应用内目录浏览器：面包屑 + 目录列表 + 「使用此目录」按钮），
**只在用户在页面里主动点开时才引导权限**，绝不启动时申请。

## 6. 回归与回滚

- P0-1：不满足条件就不设 `EXTRA_INITIAL_URI` → 等价旧行为，可单点回滚。
- P0-2：仅把"静默失败"变为"显式失败 + 字段回传"，不改变成功路径。
- P0-3：`EXTRA_LOADING` 不出现时不产生任何等待；出现时上限 1500ms。
- P0-4：线程切换沿用既有 `SCAN_EXEC`，与 BUG-14 同模式。
- P1：新增权限与方法均为**增量**；SAF 仍是默认后端，路径后端需用户显式开启，出问题可整体关闭而不影响存量用户。
