# BUG-18 万卡库加载完成后崩溃（Java 堆 OOM）修复日志

> 日期：2026-09-19 · 分支：main-v1.10（v1.10.29 发布前真机测试）
> 触发：真机（ZTE_7551N）12,100 张压测卡库，App 启动约 11 分钟后整体闪退
> 结论前置：**根因 = 全库元数据一次性上桥生成 ~45MB 桥消息，Capacitor 桥在 Java 侧处理（verbose 日志 toString + JSON 解析双份内存）把 256MB Java 堆打爆 → JNI 异常穿透 → Chromium abort → 进程死亡**。已三层修复并真机验证。

---

## 一、现象与定位过程

| 步骤 | 证据 |
|---|---|
| 闪退现象 | 真机库加载完成后的运行期（启动约 11 分钟）整 App 闪退，无提示 |
| logcat crash buffer | `signal 5 (SIGTRAP)`，backtrace #00 位于 `/product/app/webview/webview.apk!libwebviewchromium.so`，Abort message `[FATAL:jni_android.cc(306)] Please include Java exception stack in crash report` |
| dropbox + System.err（Java 栈） | `java.lang.OutOfMemoryError: Failed to allocate a 47835576 byte allocation with 25165824 free bytes and 32MB until OOM, target footprint 259734688`（堆 9% free，223MB/247MB）；帧：`StringFactory.newStringFromChars` ← `StringBuilder.toString` ← `com.getcapacitor.Bridge.callPluginMethod(Bridge.java:835)` |
| 最后一条桥调用 | `SqliteMetaPlugin.syncCards`（22:57:14），其后无成功 callback 日志 → 崩溃点即它 |
| 数据规模 | syncCards 消息 = 全库 12,100 卡元数据（path/name/creator/desc/search_text/tags…）≈ 2,400 万字符 ≈ 45MB（UTF-16） |

**关键机理**：`Bridge.callPluginMethod` 第 835 行是 Capacitor 的 verbose 日志 —— `call.getData().toString()` 会把整条消息再序列化成一个 String。万卡库内存模型下 Java 堆常态已到 223MB/247MB，此时任何一次 >25MB 的分配直接 OOM；OOM 异常抛到 Chromium JNI 边界 → abort → SIGTRAP → 进程死亡（Java 层 try/catch 无法拦截）。

**放大场景**：崩溃瞬间用户正在点开卡片（readBuffer + readThumb 渲染），与后台 reconcile 完成后的 syncCards 巨消息叠加。

---

## 二、修复（三层）

| 层 | 修复 | 文件 |
|---|---|---|
| 治本 | 所有 meta* 桥调用**分批上桥**：`META_CHUNK=800` 行/批（单条 ≤ ~3MB）；`sendMetaChunks` 串行发送、单块失败静默（下次 reconcile 自愈） | `js/mobile/sqliteMeta.js` |
| 治本 | `syncMetas` 分批语义适配：**首块 `replaceAll=true`（清幽灵卡）**，后续块仅 INSERT，避免分批 DELETE 互相摧毁 | `js/mobile/sqliteMeta.js` |
| 桥接 | `metaSyncCards(cards, replaceAll)` 透传参数（默认 true 保持旧语义） | `js/bridge/android.js` |
| 原生 | `syncCards` 新增 `replaceAll` 参数（`call.getBoolean("replaceAll", TRUE)`）；false 时跳过 DELETE all | `SqliteMetaPlugin.java` |
| 加固 | `android:largeHeap="true"`（堆上限 247MB → 512MB 级，为其它大分配场景留余量） | `AndroidManifest.xml` |

覆盖范围：`persistMetas`（增量 upsert）/ `syncMetas`（全量对齐）/ `removeMetaCards`（删除）全部走分批管道。

## 三、真机验证（ZTE_7551N / 12,100 卡）

| 项 | 修复前 | 修复后 |
|---|---|---|
| syncCards 调用模式 | 单条 ~45MB 巨消息 → 崩 | **32 条分批**（两轮各 16 批），3.5 秒完成 |
| 崩溃 | 启动 ~11 分钟 SIGTRAP | 跨过原崩溃时间点持续运行，**无 OOM / 无 FATAL** |
| Java 堆 | 223MB/247MB 濒爆 | 峰值 ~40MB |
| 回归 | - | 万卡库列表加载、进详情、世界书编辑、批量操作全正常 |

## 四、经验教训

1. **Capacitor 桥消息大小必须有约束**——任何"全库/全量"数据过桥前都要评估桥消息体积；万卡库单项全量（>1MB 量级）必须分批。
2. **verbose 日志是隐性内存放大器**——`Bridge` 每条插件调用都会把 methodData 整体 toString 打日志，消息多一份全量 String（UTF-16 双字节）。
3. **OOM 在 JNI 边界 = 必崩**——Java 层 catch 无法兜底，必须在源头控制单次分配大小。
4. **排查路径模板**：`logcat -b crash`（信号/backtrace）→ `dumpsys dropbox --print | grep <包名>`（Java 栈）→ `System.err` 完整帧 → 最后一条 `V Capacitor/Plugin: To native` 行 = 崩的那条调用。
