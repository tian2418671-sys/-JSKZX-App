# 铁律：开发流程规范

> 所有开发人员必须遵守的铁律，不可违背。

---

## 一、文档铁律

### 1.1 文档分类原则

| 分类 | 存放位置 | 可见范围 | 内容要求 |
|------|----------|----------|----------|
| **内部开发文档** | `docs/内部开发/` | 仅开发团队 | 含代码细节、数据、调试信息 |
| **用户更新文档** | `docs/用户更新/` | 用户可见 | 仅记录更新内容，不含代码和具体数字 |

### 1.2 内部开发文档规范

```
docs/内部开发/
├── BUG修复/          ← BUG 定位、根因分析、修复过程
├── 实测记录/          ← 功能实测、回归测试（可含截图/数据）
├── 技术文档/          ← 核心代码解析、技术细节
├── 方案设计/          ← 新功能方案、评审稿
├── 截图记录/          ← 实测截图（按日期分类）
└── 脚本工具/          ← 辅助脚本
```

**命名规范**：`YYYY-MM-DD_功能描述.md`

### 1.3 用户更新文档规范

```
docs/用户更新/
├── 2026-09/          ← 本月更新
└── 2026-08/          ← 历史月份
```

**命名规范**：`vX.XX.XX_更新说明.md`

**内容规范**：
- ✅ 记录新增功能、优化内容、修复的问题
- ✅ 使用用户可理解的语言描述
- ❌ 不包含代码、具体数字（内存地址、行号等）
- ❌ 不包含调试信息、内部术语

**示例**：
```markdown
# v1.10.30 更新说明

## ✨ 新增功能
- 卡片库支持网格/平铺/海报/翻页四种视图切换
- 测卡记忆支持云端同步

## 🐛 问题修复
- 修复了主题切换时动画丢失的问题
- 修复了内容指纹查重在大量卡片时崩溃的问题

## ⚡ 性能优化
- 卡片库加载速度提升 30%
- 内容指纹查重内存占用降低 60%
```

## 二、开发流程铁律

### 2.1 一条龙服务流程

> 每日开发完成后，必须执行以下流程：

```
┌─────────────────────────────────────────────────────────────┐
│                    📦 每日开发一条龙                        │
├─────────────────────────────────────────────────────────────┤
│  步骤1: 收集整理                                           │
│  ├── 收集今日更新的数据（新增功能、修改文件、测试结果）      │
│  ├── 对文档进行归类（内部开发/用户更新）                    │
│  └── 更新内部开发 README 索引                               │
│                                                             │
│  步骤2: 功能测试                                           │
│  ├── 运行 npm test 确保全部通过                             │
│  ├── 模拟器实测新功能                                       │
│  └── 截图记录关键界面                                       │
│                                                             │
│  步骤3: 代码推送                                           │
│  ├── git add .                                             │
│  ├── git commit -m "描述"                                  │
│  ├── git push jskapp main-v1.10                            │
│  └── 确保远端同步完成                                       │
│                                                             │
│  步骤4: 发布更新                                           │
│  ├── 构建 APK: npm run build:android                        │
│  ├── 更新版本号（package.json + AndroidManifest.xml）        │
│  ├── 撰写用户更新文档                                       │
│  └── 提交并推送                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 发布前检查清单

```
□ npm test 全部通过
□ 模拟器实测通过
□ 代码已 commit 并 push
□ APK 构建成功
□ 用户更新文档已更新
□ 版本号已递增
□ Git tag 已打（如需要）
□ Release notes 已生成
```

## 三、版本管理铁律

### 3.1 版本号规范

遵循语义化版本 `主版本.次版本.修订号`：
- **主版本**：重大架构变更
- **次版本**：新增功能
- **修订号**：BUG 修复、细节优化

### 3.2 版本号更新位置

| 文件 | 位置 | 示例 |
|------|------|------|
| `package.json` | `version` 字段 | `"version": "1.10.30"` |
| `android/app/build.gradle` | `versionName` | `versionName "1.10.30"` |
| `android/app/build.gradle` | `versionCode` | `versionCode 39` |

## 四、Git 提交规范

### 4.1 提交类型前缀

| 前缀 | 说明 | 示例 |
|------|------|------|
| `feat:` | 新功能 | `feat(mobile): 新增卡片库视图切换功能` |
| `fix:` | BUG 修复 | `fix(mobile): 修复内容指纹 OOM 问题` |
| `perf:` | 性能优化 | `perf(mobile): 内容指纹流式水合防 OOM` |
| `docs:` | 文档更新 | `docs: 更新用户更新日志` |
| `chore:` | 构建/工具 | `chore: 删除死代码` |
| `refactor:` | 重构 | `refactor: 重构主题切换逻辑` |
| `test:` | 测试 | `test: 新增内容指纹单元测试` |

### 4.2 提交规范

```
<type>(<scope>): <subject>

<body>

<footer>
```

**示例**：
```bash
git commit -m "fix(mobile): 修复浅色主题 Vant 变量损坏

- 修复 light 主题 21 个 --van-* 变量被冒号拼接
- 修复 SettingsView 使用 isDarkTheme 正确判断暗色主题

Closes: #17"
```

## 五、文档维护铁律

### 5.1 每日必做

- [ ] 今日开发内容归类到 `docs/内部开发/`
- [ ] 记录实测截图到 `docs/内部开发/截图记录/YYYY-MM-DD/`
- [ ] 更新 `docs/内部开发/README.md` 索引

### 5.2 发布必做

- [ ] 撰写用户更新文档到 `docs/用户更新/YYYY-MM/`
- [ ] 确保用户文档不包含代码和内部细节
- [ ] 提交并 push

---

## 六、例外条款

如有特殊情况需突破铁律，必须：
1. 在 commit message 中说明原因
2. 在团队群组中通知
3. 在下次评审会议中复盘
